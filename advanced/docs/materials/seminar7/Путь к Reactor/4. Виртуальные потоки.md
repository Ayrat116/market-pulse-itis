# 4. Виртуальные потоки: почему не они?

С JDK 21 есть ответ, который группа почти наверняка предложит сама: **виртуальные потоки**.

```java
void example() throws Exception {
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < 8; i++) {
            executor.submit(() -> client.fetchQuotes());   // тот же БЛОКИРУЮЩИЙ клиент
        }
    }   // close() дожидается завершения всех задач
}
```

Один и тот же сценарий — 8 запросов к серверу с задержкой 300 мс (реальный замер на этой машине):

| Вариант | Потоков ОС | Время на 8 запросов |
|---|---|---|
| `HttpURLConnection` + пул из 3 потоков | 3 | 937 мс |
| `HttpURLConnection` + виртуальные потоки | ≈ несколько (carrier-потоки) | 317 мс |
| `Reactor` (один поток цикла) | 1 | 339 мс |

Честный вывод: на такой задаче виртуальные потоки **не уступают** реактору, а код остаётся
линейным и блокирующим. Зачем тогда Reactor на семинаре?

| Причина | Пояснение |
|---|---|
| Это механизм «под капотом» | при блокирующем `read()` виртуальный поток паркуется, а ожидание готовности сокета в JDK внутри реализовано теми же `epoll`/`kqueue` — то, что мы разбираем дальше |
| На нём построена большая часть экосистемы | Netty, Vert.x, Spring WebFlux, Reactor Netty — событийные циклы на `Selector` |
| Понимание ограничений | нельзя блокировать поток цикла; backpressure; почему «асинхронный стиль» устроен так |
| Модель не вытеснена | виртуальные потоки — удобство для разработчика, Reactor — архитектура ввода-вывода |

| | Реактор | Виртуальные потоки |
|---|---|---|
| Стиль кода | колбэки/`CompletableFuture`, конечный автомат | обычный линейный блокирующий код |
| Стоимость одного ожидания | запись в `Selector` | парковка легковесного потока |
| Когда проще | высоконагруженные сетевые серверы, протоколы со своим состоянием | прикладной код с блокирующими библиотеками |
