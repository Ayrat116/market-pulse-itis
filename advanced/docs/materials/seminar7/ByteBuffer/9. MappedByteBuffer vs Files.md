# 9. MappedByteBuffer vs Files: замер

```java
void example() throws IOException {
    byte[] all = Files.readAllBytes(path);               // весь файл копируется в кучу

    try (FileChannel channel = FileChannel.open(path, StandardOpenOption.READ)) {
        MappedByteBuffer mapped = channel.map(
                FileChannel.MapMode.READ_ONLY, 0, channel.size());   // копии в кучу нет
        long sum = 0;
        while (mapped.hasRemaining()) {
            sum += mapped.get();                          // страницы подгружаются по мере обращения
        }
    }
}
```

**Бенчмарк** — JMH, `MappedFileReadingBenchmark`, режим `avgt` и профилировщик `-prof gc`; тестовые
данные — синтетический файл ≈ 23 МБ (для занятия заменить на реальный текст, например главу
«Войны и мира»):

| Бенчмарк | Время, мкс/операция | Аллокации, Б/операция | GC-пауз за прогон |
|---|---|---|---|
| `readAllBytes` | ≈ 11 900 | ≈ 62 500 000 | 57 |
| `mappedByteBuffer` (с проходом по байтам) | ≈ 40 300 | ≈ 1 100 | ≈ 0 |

| Критерий | Победитель | Разница |
|---|---|---|
| Время одного полного чтения | `readAllBytes` | ≈ в 3,4 раза быстрее |
| Аллокации в куче | `MappedByteBuffer` | ≈ в 56 000 раз меньше |
| Нагрузка на GC | `MappedByteBuffer` | паузы отсутствуют |

Почему `mappedByteBuffer` медленнее по времени в этом тесте: проход по `get()` байт за байтом
дороже одного объёмного копирования памяти, которое делает `readAllBytes`. Выгода отображения —
память и GC, а не скорость одного чтения.

| Выбирать `MappedByteBuffer`, когда | Выбирать `Files.readAllBytes`/`lines`, когда |
|---|---|
| файл большой, читают часть или многократно по произвольным смещениям | файл небольшой, нужен целиком один раз |
| важны GC-паузы и размер кучи | важна простота и предсказуемая задержка |
| нужен общий доступ нескольких процессов к одним данным | достаточно обычного последовательного чтения |
